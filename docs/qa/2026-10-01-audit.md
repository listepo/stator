## 2. Test plan

1. **Bootstrap.** Locked worktree from `origin/main`, `pnpm install --frozen-lockfile`.
2. **Regression = CI parity.** Run every step of `pnpm run ci` one at a time (same order as
   `ci.sh`, each logged on its own) plus `pnpm run test:ffi`, which is its own CI job.
3. **Smoke.** `stator --help`, `--version`, `build` + run of a trivial program, `explain --json`.
4. **CLI/driver functional + negative.** Output paths that alias the input or each other,
   missing directories, flags with no value, flags swallowed as values, flags that don't apply
   to the command, bad `STATOR_OPT`, a directory or non-TS file as the entry.
5. **Environment handling.** `.env` in the project directory vs real env for `CC`,
   `STATOR_RUNTIME`, `STATOR_RUNTIME_ROOT`, `STATOR_OTEL` (unreachable endpoint).
6. **Differential semantics.** 47 one-line probes (numbers, strings, arrays, JSON, Math, regexp,
   Date, console formatting). Each compiles alone; where it compiles, binary output must be
   byte-identical to `node` on the same file.
7. **Runtime robustness.** Deep recursion, large loops (string `+=`, `push`, `Map`), memory/time.
8. **Gate/lowering agreement.** Constructs the docs list as `not-yet` must never surface as an
   internal (`STA40xx`) diagnostic.
9. **FFI.** `ffi-gen` argument validation, `@statorLink` pragma handling, generated `#include`/`#line`.
10. **Site (UI/UX + cross-browser + light load).** Build `site/` into `/tmp`, serve it on
    127.0.0.1, then check with Playwright + Chrome: status, console errors, broken anchors,
    `alt` text, theme cycle and persistence, blocked `localStorage`, widths 320/360/375/414,
    `prefers-color-scheme: dark`, JS disabled, and external requests (aborted, recorded only).
11. **Security review** as listed in the applicability table. Find and describe only; nothing
    was exploited. Probes used harmless local stand-ins (a fake `CC` script that only writes a
    marker file).

### F1. Output paths may alias the entry/each other: `build` silently overwrites source files

- **Severity:** high
- **Impact:** a typo or tab-completion slip (`-o app.ts`, `--emit-header=lib.ts`) wipes a source
  file with generated C, and the command exits 0. Uncommitted work is lost. `--keep-c` writes
  `<out>.c` without checking, so `-o app` silently replaces a hand-written `app.c` next to it.
  `--emit-header` equal to `-o` makes the header overwrite the C (or object) just written.
- **Environment:** common (above).
- **Steps to reproduce:**
  1. `printf 'const x: number = 1 + 2;\nconsole.log(x);\n' > app.ts`
  2. `stator build app.ts -o app.ts --emit=c; echo $?`
  3. `head -3 app.ts`
  4. `printf 'export function add(a: number, b: number): number { return a + b; }\n' > lib.ts`
  5. `stator build lib.ts -o lib.c --emit=c --emit-header=lib.ts; echo $?`, then look at `lib.ts`
- **Expected result:** the build refuses with a `STA0004`-style usage error ("output path is the
  entry file" / "--emit-header and -o name the same file") and leaves every input untouched.
- **Actual result:** exit 0. `app.ts` now starts with `#include "jsrt_value.h"`, and `lib.ts`
  is replaced by the header. With `-o lib.h --emit-header=lib.h` the C output is silently lost.
- **Evidence:**
  ```
  --- A: -o == entry with --emit=c
  exit=0
  #include "jsrt_value.h"
  JSRT_GLOBALS(1);
  SOURCE OVERWRITTEN (     406 bytes)
  --- emit-header == entry
  exit=0
  lib.ts OVERWRITTEN
  ```
- **Missing check:** `packages/compiler/src/cli/main.ts:243-262` (`parse` validates that
  `entry`/`out` exist, never that they differ); `packages/compiler/src/cli/build.ts:189-198`
  (`writeFileSync(options.out …)` / `writeFileSync(options.emitHeader …)` with no alias check);
  `build.ts:203` and `build.ts:218` (`${options.out}.c` written without checking that it doesn't
  already exist or isn't an input).
- **Suggested fix:** in `build()` (so in-process callers are covered too), compare
  `realpath`/`resolve` of `entry`, every program source file, `out`, `emitHeader` and
  `${out}.c` (when `--keep-c`). If any two collide, throw `BuildError('STA0004', …)` before
  compiling. Optionally refuse to overwrite an existing `${out}.c` unless it was produced by
  stator (header marker).
- **Proposed test:**
  ```ts
  test('build refuses an -o that is the entry file (source must survive)', async () => {
    const dir = scratch();
    const entry = join(dir, 'app.ts');
    writeFileSync(entry, 'console.log(1);\n');
    const r = await stator(['build', entry, '-o', entry, '--emit=c']);
    assert.equal(readFileSync(entry, 'utf8'), 'console.log(1);\n', 'entry overwritten with C');
    assert.equal(r.status, 1);
  });

  test('--emit-header refuses to alias -o', async () => {
    const dir = scratch();
    const entry = join(dir, 'lib.ts');
    writeFileSync(entry, 'export function add(a: number, b: number): number { return a + b; }\n');
    const h = join(dir, 'lib.h');
    const r = await stator(['build', entry, '-o', h, '--emit=c', `--emit-header=${h}`]);
    assert.equal(r.status, 1, 'the header silently replaced the C output');
  });
  ```

### F2. Unwritable output path is reported as STA4072 "compiler bug"

- **Severity:** medium
- **Impact:** a missing output directory, a read-only location or a full disk (this host was
  nearly full before the audit) is the user's to fix. Instead the CLI calls it a compiler bug
  and asks for a bug report. That misleads users, produces noise reports, and breaks the
  documented contract that STA4072 is only for real escaping exceptions (`docs/DIAGNOSTICS.md`,
  STA4072 row).
- **Environment:** common.
- **Steps to reproduce:**
  1. `printf 'console.log(1);\n' > app.ts`
  2. `stator build app.ts -o ./nope/out.c --emit=c; echo $?` (where `./nope` doesn't exist)
- **Expected result:** a stable user-error code (e.g. a new `STA0014 cannot write output
  "<path>": ENOENT`) with no "compiler bug" wording. Exit 1.
- **Actual result:** `STA4072 internal error: ENOENT … — this is a compiler bug; report it with
  the input that triggered it`. The same happens for `--emit-header` and for the `--keep-c`
  `.c` file. For a link into a missing directory, clang fails and the message again says
  "this is a compiler bug" (`linkFailure`).
- **Evidence:**
  ```
  stator: STA4072 internal error: ENOENT: no such file or directory, open
  '/tmp/stator-qa/work/nope/out.c' — this is a compiler bug; report it with the
  input that triggered it
  exit=1
  ```
- **Missing check / error handling:** `packages/compiler/src/cli/build.ts:190`, `:192`,
  `:198`, `:205`, `:221` (bare `writeFileSync`, no `try/catch`) reach the catch-all at
  `packages/compiler/src/cli/main.ts:333-342`. `build.ts:577-595` (`linkFailure`) doesn't
  check that `dirname(out)` exists before blaming the compiler.
- **Suggested fix:** wrap output writes in one `writeOutput(path, text)` helper that converts
  `ENOENT`/`EACCES`/`EROFS`/`ENOSPC`/`EISDIR` into a `BuildError` with a user-facing code. Check
  `existsSync(dirname(out))` before invoking clang.
- **Proposed test:**
  ```ts
  test('an unwritable -o is a user error, not STA4072 "compiler bug"', async () => {
    const dir = scratch();
    const entry = join(dir, 'app.ts');
    writeFileSync(entry, 'console.log(1);\n');
    const r = await stator(['build', entry, '-o', join(dir, 'missing', 'out.c'), '--emit=c']);
    assert.equal(r.status, 1);
    assert.doesNotMatch(r.stderr, /STA4072|compiler bug/);
  });
  ```

### F3. `STATOR_RUNTIME`/`STATOR_RUNTIME_ROOT` read at import time: gate and linker disagree; binary links then panics

- **Severity:** medium
- **Impact:** `support/features.ts` promises that the gate and the linked archive "cannot
  disagree" and that the flavor is read at **call** time. But `build.ts` freezes the flavor,
  runtime root and archive path at **module load**, which happens before `main()` calls
  `dotenvConfig()`. So `STATOR_RUNTIME=intl` in a `.env` (which the CLI explicitly supports)
  turns the ICU-only methods on in the gate, while the program links against the **default**
  archive. The build exits 0, and the binary aborts on first use (exit 134). In-process
  callers that set the variable around one build (the documented test pattern; the Test262
  runner calls `build()` in-process) hit the same split. `STATOR_RUNTIME_ROOT` in `.env` is
  silently ignored.
- **Environment:** common. Only the default runtime archive is built.
- **Steps to reproduce:**
  1. `printf "console.log('a'.localeCompare('b', 'en'));\n" > lc.ts`
  2. `stator build lc.ts -o lc0`: correctly refused with `STA1215` (needs the ICU build)
  3. `STATOR_RUNTIME=intl stator build lc.ts -o lc1`: correctly `STA0011 runtime archive not found … build-intl/libjsrt.a`
  4. `echo STATOR_RUNTIME=intl > .env && stator build lc.ts -o lc2; echo $?`
  5. `./lc2; echo $?`
- **Expected result:** step 4 behaves like step 3 (same variable, same answer), either STA0011
  or a link against `build-intl`.
- **Actual result:** step 4 exits 0 and step 5 panics:
  ```
  exit=0
  PANIC: STA2005: the locale-sensitive string methods need the ICU feature build; rebuild with
  `just runtime-intl` and compile with STATOR_RUNTIME=intl
  Shadow stack depth: 1 frames
  exit=134
  ```
- **Evidence:** the log above. With `.env` containing `STATOR_RUNTIME_ROOT=/nonexistent-root`,
  the fake-CC probe from F4 shows clang still received
  `-I …/_worktrees/stator-qa/packages/runtime/include`, so the override was ignored.
- **Missing check:** `packages/compiler/src/cli/build.ts:127-154`. `RUNTIME_ROOT`,
  `RUNTIME_INCLUDE`, `FLAVOR`, `SANITIZED`, `RUNTIME_LIB_DIR` and `RUNTIME_ARCHIVE` are
  module-level `const`s, evaluated at import time and before
  `packages/compiler/src/cli/main.ts:313` (`dotenvConfig`). There's no check that the gate's
  `intlEnabled()` (`frontend/gate.ts:2554`) and the link's `FLAVOR` agree.
- **Suggested fix:** compute flavor/root/archive inside `build()` (one `resolveRuntime()` call
  per build, passed to both the gate and `link`). Or load `.env` before importing `build.ts`
  (a tiny bootstrap entry that dynamic-imports the CLI after `dotenvConfig`). Add an assertion
  in `link()` that the flavor the gate used equals the archive flavor.
- **Proposed test:**
  ```ts
  test('STATOR_RUNTIME from .env must reach the link, not only the gate', NATIVE_ONLY, async () => {
    const dir = scratch();
    writeFileSync(join(dir, '.env'), 'STATOR_RUNTIME=intl\n');
    writeFileSync(join(dir, 'lc.ts'), "console.log('a'.localeCompare('b', 'en'));\n");
    const b = await stator(['build', 'lc.ts', '-o', 'lc'], dir, { STATOR_RUNTIME: undefined });
    if (b.status === 0) {
      const r = await run(join(dir, 'lc'), [], dir);
      assert.equal(r.status, 0, `linked against the default archive and panicked:\n${r.stderr}`);
    }
  });
  ```

### F4. Project-local `.env` can choose the C compiler (and telemetry endpoint) for `stator build`

- **Severity:** medium (security: OWASP A05 security misconfiguration / A08 software and data
  integrity)
- **Impact:** `main()` loads `.env` from the **current working directory**, so whoever wrote
  the project being compiled controls `CC`. Running `stator build` (even `--emit-header`, which
  only compiles an object and never runs the result) inside a cloned repo runs whatever
  executable its `.env` names. The same file can set `STATOR_OTEL` +
  `OTEL_EXPORTER_OTLP_ENDPOINT`/`_HEADERS`, which sends span data (entry path, error messages)
  to a third-party host, and can set `STATOR_OPT`/`STATOR_RUNTIME` (see F3). Users don't expect
  a compiler to take toolchain selection from the input tree. Nothing is printed when `.env`
  values are applied. Found and described only: the probe used a local script that just writes
  a marker file.
- **Environment:** common. `CC` unset in the real environment.
- **Steps to reproduce:**
  1. In an empty directory create `fakecc.sh` (`#!/bin/sh` + `echo "fake-cc ran with: $*" > cc-marker.txt`), `chmod +x`.
  2. `printf 'CC=%s/fakecc.sh\n' "$PWD" > .env`
  3. `printf 'export function add(a: number, b: number): number { return a + b; }\n' > lib.ts`
  4. `env -u CC stator build lib.ts -o lib.o --emit-header=lib.h; echo $?; cat cc-marker.txt`
- **Expected result:** toolchain and telemetry variables come only from the real environment,
  or at least from `.env` only with an explicit opt-in flag and a visible notice.
- **Actual result:** the script from `.env` is executed, and the build reports success (exit 0)
  even though no object was produced.
- **Evidence:**
  ```
  exit=0
  fake-cc ran with: -std=c11 -O2 -I …/packages/runtime/include -c /var/folders/…/T/stator-LmuPn7/module.c -o lib.o
  ```
- **Missing check:** `packages/compiler/src/cli/main.ts:313` (`dotenvConfig({ quiet: true })`
  with the default `path` = `process.cwd()/.env`, no allowlist); `packages/compiler/src/cli/build.ts:404-411`
  (`selectCC` trusts `process.env.CC`); `packages/compiler/src/support/telemetry.ts:24-41`
  (exporter configured from the same env). `build.ts:469-492` (`compileObject`) doesn't
  verify that `out` exists after a zero exit.
- **Suggested fix:** load `.env` only from the stator installation/workspace root (or only when
  `--env-file` is passed), and apply only an allowlist (`STATOR_OTEL`, `OTEL_*` behind
  opt-in). Never take `CC`/`STATOR_RUNTIME_ROOT` from it. Print one stderr line naming the
  `.env` keys applied. After clang returns 0, check `existsSync(out)`.
- **Proposed test:**
  ```ts
  test('a project .env must not choose the C compiler', NATIVE_ONLY, async () => {
    const dir = scratch();
    const marker = join(dir, 'ran.txt');
    const fake = join(dir, 'fakecc.sh');
    writeFileSync(fake, `#!/bin/sh\necho ran > "${marker}"\n`);
    chmodSync(fake, 0o755);
    writeFileSync(join(dir, '.env'), `CC=${fake}\n`);
    writeFileSync(join(dir, 'lib.ts'), 'export function add(a: number, b: number): number { return a + b; }\n');
    await stator(['build', 'lib.ts', '-o', 'lib.o', '--emit-header=lib.h'], dir, { CC: undefined });
    assert.equal(existsSync(marker), false, 'CC from the project .env was executed');
  });
  ```

### F5. BigInt literal yields internal STA4031 instead of the documented not-yet STA1213

- **Severity:** low (already tracked as an `@expected-fail` subset fixture, but the
  user-visible contract is wrong)
- **Impact:** `docs/SUBSET.md:125` and `:319` promise `not-yet(STA1213, Phase 5)` for every
  BigInt use. Instead any `1n` gets **STA4031 "internal"**, a code that by definition means "the
  gate accepted and the lowering cannot lower — the two disagree", in both modes, in `build`
  and `explain --json`. Tools keyed on `verdict`/`code` (the decision tests, editors) see an
  internal error rather than a planned gap. STA1213 doesn't appear anywhere in
  `packages/compiler/src`.
- **Environment:** common. Both `--mode=ts` and `--mode=js`.
- **Steps to reproduce:**
  1. `echo 'const b = 1n;' > b.ts`
  2. `stator explain b.ts --json`

### F6. Unbounded recursion in compiled code segfaults (SIGSEGV, exit 139), no RangeError, no diagnostic

- **Severity:** medium
- **Impact:** in Node, deep recursion throws a catchable `RangeError: Maximum call stack size
  exceeded`. A stator binary instead dies with SIGSEGV and prints nothing. `try/catch` can't
  recover, there's no message, and on hosts with smaller thread stacks a recursion depth that
  works on the dev box crashes in production. It also breaks the project's own rule that
  every runtime gap is "loud" (`STA2005`).
- **Environment:** common. Default runtime (Boehm GC), `-O2`.
- **Steps to reproduce:**
  1. `printf 'function f(n: number): number { return n === 0 ? 0 : 1 + f(n - 1); }\nconsole.log(f(1000000));\n' > p2.ts`
  2. `stator build p2.ts -o p2 && ./p2; echo $?`
  3. `node p2.ts`
- **Expected result:** a catchable `RangeError` (Node parity), or at minimum a deterministic
  `PANIC: STA2005 … stack overflow` with the shadow-stack depth, as other runtime refusals do.
- **Actual result:** exit 139 (SIGSEGV), empty stdout and stderr, after 0.21 s.
- **Evidence:** `exit=139 … 11075584 maximum resident set size`. Node prints
  `RangeError: Maximum call stack size exceeded at f (…/p2.ts:1:33)`.
- **Missing check:** no stack-depth guard in `JSRT_FRAME`
  (`packages/runtime/include/jsrt_value.h:1686`) or in function prologues emitted by
  `packages/compiler/src/codegen/index.ts`. No `sigaltstack`/SIGSEGV handler anywhere in
  `packages/runtime/src` (`rg sigaltstack` finds nothing).
- **Suggested fix:** the shadow stack already counts frames. Have `JSRT_FRAME` compare the
  depth (or `__builtin_frame_address(0)` against a limit computed at `jsrt_init` from
  `pthread_get_stacksize_np`/`getrlimit`) and call `jsrt_throw_error(&jsrt_class_range_error,
  "Maximum call stack size exceeded")`. As a fallback, install a `sigaltstack` SIGSEGV handler
  that prints a `PANIC: STA2005 stack overflow` line.
- **Proposed test:**
  ```ts
  test('unbounded recursion fails with a diagnostic, not SIGSEGV', NATIVE_ONLY, async () => {
    const dir = scratch();
    writeFileSync(join(dir, 'r.ts'),
      'function f(n: number): number { return n === 0 ? 0 : 1 + f(n - 1); }\nconsole.log(f(1000000));\n');
    const b = await stator(['build', join(dir, 'r.ts'), '-o', join(dir, 'r')]);
    assert.equal(b.status, 0, b.stderr);
    const r = await run(join(dir, 'r'), []);
    assert.equal(r.signal, undefined, `killed by ${String(r.signal)}`);
    assert.match(r.stderr, /RangeError|stack/i);
  });
  ```

### F9. `@statorLink` flags from any `.d.ts` reach clang verbatim (build-time flag injection)

- **Severity:** low (security, supply chain; confirmed by code review, deliberately **not
  exercised**)
- **Impact:** `collectLinkFlags` walks **every** declaration file in the program, including
  ones pulled in from dependencies, and appends their `@statorLink` words to the single
  clang command that compiles **and** links. Any flag is accepted: `-fplugin=<so>` and
  `-Xclang -load -Xclang <so>` load code into clang at build time, `-o <path>` redirects
  output, `-Wl,…` passes anything to the linker. Running the resulting binary already trusts
  the dependency, but `stator build` itself (and CI that only builds) is a separate trust step
  that users don't expect to execute dependency-chosen code. The only constraint is that the
  file declares one `@statorExtern` function.
- **Environment:** code review of `d1ed3d1`.
- **Steps to reproduce (review only):**
  1. Read `packages/compiler/src/frontend/extern.ts:495-508`: every word after the marker
     becomes a `flags` entry, with only `#…` and unbalanced `"` refused.
  2. Read `extern.ts:574-587`: `program.getSourceFiles()` → every `.d.ts` with an extern.
  3. Read `packages/compiler/src/cli/build.ts:517-534`: the flags are spread into clang's argv
     after the source file.
- **Expected result:** pragma flags are limited to link-only flags (`-l<name>`, `-L<dir>`,
  `-framework <name>`, `-Wl,-rpath,<dir>`), and anything else is refused (STA1119) unless the
  user passes it via `--link=`.
- **Actual result:** no allowlist. Flags are passed through as written.
- **Evidence:** code paths above. `docs/FFI.md §9` documents "verbatim clang link flags".
- **Missing check:** `packages/compiler/src/frontend/extern.ts:508` (`return { kind: 'flags', flags: words, … }`
  with no per-flag validation).
- **Suggested fix:** an allowlist in `parseLinkPragmaBody`, with a STA1119 refusal naming the
  flag. Keep `--link=` as the explicit escape hatch for anything else.

### F12. String `+=` in a loop is quadratic; `jsrt_string_concat` returns `JSRT_NULL` on overflow

- **Severity:** low (performance; the overflow branch is **suspected**, not reproduced: it
  needs >4 G code units)
- **Impact:** the most common string-building idiom costs O(n²). 200k one-character appends
  take 2.74 s vs Node's 0.07 s (~40×), and 400k take 9.6 s. Compiled programs end up slower
  than the interpreter they replace, which goes against the project's pitch. Separately, on
  length overflow the function returns `JSRT_NULL`, which callers then use as a string, where
  the spec requires `RangeError: Invalid string length`.
- **Steps to reproduce:**
  1. `printf "let s: string = '';\nfor (let i = 0; i < 200000; i++) { s += 'x'; }\nconsole.log(s.length);\n" > p4.ts`
  2. `stator build p4.ts -o p4 && /usr/bin/time ./p4`, then `/usr/bin/time node p4.ts`
  3. Repeat with 50k/100k/400k.
- **Expected result:** roughly linear time (rope or capacity-doubling append buffer), close to Node.
- **Actual result:** 50k 0.39 s, 100k 0.90 s, 200k 2.74 s, 400k 9.63 s (quadratic). Node 0.07 s at 200k.
- **Missing check / error handling:** `packages/runtime/src/jsrt_string.c:424-452` (copies
  both operands on every concat); `jsrt_string.c:429-431` returns `JSRT_NULL` instead of
  throwing. No Node-style max-length cap (Node: 2^29-24) like the one `repeat`/`padStart`
  already enforce in `jsrt_string_ops.c`.
- **Suggested fix:** throw `RangeError` via `jsrt_throw_error(&jsrt_class_range_error,
  "Invalid string length")` past the same cap `jsrt_string_ops.c` uses. For speed,
  `docs/VALUE.md` §12 already anticipates ropes: implement a flat-on-read rope or an in-place
  append when the left operand is uniquely referenced and has spare capacity.
